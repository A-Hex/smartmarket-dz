# Deploying to Render

This repo includes a `render.yaml` Blueprint that provisions everything needed for a **preview/demo**
deployment: a Postgres database, the FastAPI backend, and the Next.js frontend — all on Render's free tier.

## What's deliberately left out, and why

- **No Redis, no Celery worker.** Nothing in the codebase currently dispatches a job to Celery — every
  analytics/cleaning job runs synchronously inside the API request (see the main README's "What's left").
  Deploying a worker would just be a paid instance sitting idle. Add it back once real async dispatch exists.
- **No persistent disk.** Uploaded datasets and generated reports live on local disk and are **not persistent**
  on Render's free web service tier — they're lost on every redeploy or restart. Fine for a preview; if you need
  uploads to survive restarts, add a paid disk to the backend service in the Render dashboard (or in `render.yaml`
  under that service's `disk:` key) and point `UPLOAD_DIR`/`REPORT_DIR` at a path inside it.

## Steps

1. **Push this repo to GitHub** (Render deploys from a Git repo, not a local folder).

2. **Create the Blueprint**: in the Render dashboard, click **New → Blueprint**, connect the repo, and Render
   will read `render.yaml` and propose the three resources (database + 2 web services). Click **Apply**.

3. **First deploy will take a few minutes.** The backend's start command runs `alembic upgrade head` before
   `uvicorn`, so the database schema is created automatically — no manual migration step needed. If the very
   first deploy fails because the backend started before the database finished provisioning, just click
   **Manual Deploy** on the backend service to retry — this is a known first-deploy race on Render's Blueprint
   flow, not something wrong with this repo.

4. **Check the actual assigned URLs.** `render.yaml` predicts the service URLs as `https://smartmarket-backend.onrender.com`
   and `https://smartmarket-frontend.onrender.com` (Render service names are globally unique — if either name is
   already taken by someone else, Render will suffix it, e.g. `smartmarket-backend-a1b2.onrender.com`). If that
   happens:
   - Update `CORS_ORIGINS` on the **backend** service to the real frontend URL.
   - Update `NEXT_PUBLIC_API_URL` on the **frontend** service to the real backend URL + `/api/v1`.
   - `NEXT_PUBLIC_API_URL` is a *build-time* variable (Next.js inlines it into the client bundle) — after changing
     it, trigger a **manual redeploy** of the frontend, not just a restart.

5. **Seed demo data (optional).** Render's dashboard has a **Shell** tab per service. Open it on the backend
   service and run:
   ```bash
   python -m app.db.seed
   ```
   This creates a demo company/user (`demo@smartmarket.dz` / `Demo12345!`) and a synthetic Algerian retail CSV
   in the backend's local storage — upload it through the UI once logged in to exercise the full pipeline.
   Since storage isn't persistent, you'll need to re-run this after any redeploy if you want the demo data back.

6. **Free tier services spin down after inactivity** and take ~30–60s to wake back up on the next request — the
   first load after a period of inactivity will feel slow. This is normal Render free-tier behavior, not a bug.

## Environment variables you may want to change

| Variable | Where | Why |
|---|---|---|
| `SECRET_KEY` | backend | Auto-generated by `generateValue: true` in the Blueprint — you don't need to touch this, but never reuse it elsewhere. |
| `CORS_ORIGINS` | backend | Must match the frontend's real URL exactly (see step 4). |
| `NEXT_PUBLIC_API_URL` | frontend | Must match the backend's real URL + `/api/v1` (see step 4). |

## If you outgrow the free tier

- Upgrade the Postgres plan (free Postgres on Render expires after 90 days and needs recreating otherwise).
- Add a paid disk to the backend for persistent file storage.
- Add a Redis instance + a `type: worker` service running `celery -A app.jobs.celery_app worker --loglevel=info`
  once real Celery task dispatch is implemented (see the main README).
